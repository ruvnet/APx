# ADR 004: Separate MetaHarness execution from APx measurement

Status: accepted for the APx reference implementation.

## Decision

Use MetaHarness Darwin as the controlled task execution surface and APx as the measurement and promotion surface. Compile versioned APx task packs into native Darwin suites. Freeze the human baseline, evaluator and environment separately. Bind each evaluation and promotion result to a hashed campaign envelope.

The APx MetaHarness wrapper validates command fields but never executes them. External native MetaHarness runs trusted repository tasks and returns receipts. The APx kernel decides credit and promotion without granting deployment authority.

## Rationale

Combining execution and scoring gives a candidate a larger path to influence its own exam. Separation creates a clear trust boundary and lets the APx scorer stay dependency free. It also permits different controlled runners to emit the same receipt contract.

## Alternatives

| Choice | Delivery cost | Security | Reproducibility | Result |
| --- | ---: | ---: | ---: | --- |
| APx executes arbitrary commands | Low | Low | Medium | Rejected because receipt input could become code execution |
| MetaHarness score replaces APx | Medium | Medium | High | Rejected because task success does not measure human reference throughput |
| Separate runner and scorer | Medium | High | High | Selected |

## Consequences

Operators must configure two connected stages and preserve their receipts. The boundary improves auditability and allows the scoring kernel to reject evidence without needing source repository, shell, model or network access.

The visible development pack cannot act as a holdout. Production use requires an independently controlled holdout pack, measured human cohort and qualified adjudicators.

## Rollback

Compiled suites and campaign envelopes are immutable artifacts. Operators can replay a campaign with earlier compiler and scorer versions. A schema change requires a new version rather than silently changing existing evidence.

## Acceptance tests

The compiler must reject invalid source pins, shared selection and holdout identities, duplicate task IDs, multiline commands and tampered envelopes. Native Darwin must verify the compiled suite hash.
